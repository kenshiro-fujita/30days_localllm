# Day19 最小RAG実装と3モデル比較

学習日: 2026-08-04

## 目的

Day18で作成したチャンク分割とベクトル検索を回答生成までつなぎ、最小RAGを完成させる。検索条件を共通にし、以下の3モデルへ同じ根拠を渡して回答を比較する。

- TinySwallow 1.5B（Ollama）
- EvoLLM-JP-v1-7B 4bit（MLX）
- RLT-7B 4bit（MLX）

## 成果物

- `rag/rag_qa.py`

Codexがコード案を作成し、ユーザーがVS Codeへ入力・保存して構文確認と2回の比較実験を行った。

## 実装した流れ

```text
notes/day14_api_summary.mdを読み込む
→ 500文字で6チャンクに分割
→ bge-m3で質問と各チャンクをEmbedding
→ コサイン類似度の上位3件を取得
→ 同じ根拠を含むRAGプロンプトを作成
→ TinySwallow、EvoLLM-JP、RLT-7Bへ順番に送信
→ 回答と所要時間を表示
```

TinySwallowはOllamaの`/api/chat`、EvoLLM-JPとRLT-7Bは`mlx-lm`のPython APIで呼び出した。MLXモデルは1本ずつ読み込み、回答後に解放した。

全モデルへ次の共通指示を与えた。

```text
あなたは、与えられた根拠だけを使って質問に答えるアシスタントです。
根拠に答えがない場合は、推測せず「根拠からは分かりません」と答えてください。
日本語で簡潔に回答してください。
```

## 構文確認

```bash
python -m py_compile rag/rag_qa.py
```

何も表示されず終了し、構文エラーがないことを確認した。

## 実験1: 根拠に答えがある質問

質問:

```text
OpenAI互換APIとは何ですか？
```

検索上位3件のスコアは`0.7129`、`0.6611`、`0.5503`だった。1位には直接的な定義が含まれたが、固定文字数分割によって先頭の`OpenAI`が`penAI`になっていた。

### TinySwallow

```text
OpenAI互換APIは、OllamaというローカルLLMと通信するためのインターフェースです。

具体的には、

1. **リクエスト形式:** OpenAIが提供する特定のフォーマットでリクエストを送信します。
2. **レスポンス形式:** Ollamaから返されるレスポンスも、OpenAI互換APIに準拠した形式になります。

このようにして、OllamaはOpenAIのモデルと同じような機能を利用できるようになっています。
```

所要時間は14.61秒だった。構造化されて読みやすいが、「Ollamaと通信するため」と狭く定義し、互換範囲が限定される点も落とした。

### EvoLLM-JP

```text
OpenAI互兼APIとは、OpenAIのAPI形式を模倣したAPIです。これにより、OpenAIのAPIを使用しているPythonアプリケーションやライブラリを、ローカルのTinySwallowに接続できます。
```

所要時間は13.60秒だった。短く要点をまとめたが、`互兼`という誤字があり、一般的な定義を今回のTinySwallow構成へ寄せすぎた。

### RLT-7B

```text
OpenAI互換APIとは、OpenAIが提供するモデルとサーバーとの間の通信規約を模倣したAPI形式です。ただし、これはOpenAIのモデルやサーバーを使うことを意味するものではなく、OpenAI形式のリクエストを処理できるように設計されています。具体的には、`model`や`messages`などのパラメータを送信して回答を得る方法が同じように扱われています。しかし、実際の接続先はOpenAIではなく、ローカルのOllamaサーバー（`localhost:11434`）に変更されています。つまり、このAPI形式はOpenAIのAPIと互換性があるように設計されているが、実際には別のソフトウェア（Ollama）と通信を行っていることを示しています。
```

所要時間は12.48秒だった。「形式が互換でもOpenAIのモデルやサーバーを使うわけではない」という重要点を拾い、今回の3モデルでは最も根拠に忠実だった。

## 実験2: 根拠に答えがない質問

質問:

```text
今日の東京の天気は何ですか？
```

検索上位3件のスコアは`0.3237`、`0.3228`、`0.3198`と低く、天気の情報は含まれていなかった。

### TinySwallow

```text
根拠からは分かりません。
```

所要時間は1.07秒だった。指示どおり、簡潔に回答を拒否した。

### EvoLLM-JP

```text
今日の東京の天気は、晴れ。
```

所要時間は10.91秒だった。根拠に天気情報がないにもかかわらず、晴れと断定した。

### RLT-7B

```text
根拠からは分かりません。根拠には具体的な天気予報の情報は含まれていません。根拠はPythonアプリとOllamaの通信プロセスについて説明していますが、実際の天気予報の回答はモデルによって生成される可能性があります。しかし、根拠にはTinySwallowが東京の天気を予報する内容は含まれていません。したがって、根拠から東京の天気を特定することはできません。
```

所要時間は9.94秒だった。回答を拒否できたが、「簡潔に」という指示に対しては長かった。

## 結論

- RAGで根拠を渡しても、モデルが根拠だけを使うとは限らない。
- 答えがある質問ではRLT-7Bが最も根拠に忠実だった。
- 答えがない質問ではTinySwallowが最も簡潔かつ正しく拒否した。
- EvoLLM-JPは、根拠にない天気を断定するハルシネーションが発生した。
- 固定文字数分割による単語の分断は、回答生成段階にも影響する。
- 類似度が低くても現在の実装は上位3件を必ず渡すため、最低スコアによる足切りが改善候補になる。
- 今回の所要時間にはMLXモデルの読み込みも含まれ、1回だけの結果なので速度の優劣は決めない。
