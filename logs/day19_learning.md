# Day19 学習メモ

## 今日のテーマ

Apple Silicon向けのMLXを導入し、EvoLLM-JP-v1-7BとRLT-7Bを4bit量子化して動かした。正式Day19では、Markdown文書を検索し、同じ根拠をTinySwallow、EvoLLM-JP、RLT-7Bへ渡す最小RAGを実装した。

## 今日理解したこと

- MLXはApple Silicon向けの機械学習基盤で、`mlx-lm`を使うとHugging FaceのLLMをMLX形式へ変換し、量子化や推論ができる。
- OllamaとMLXは上下関係ではなく、ローカルLLMを動かす別の実行ルートである。
- `ollama list`に表示されるのはOllamaが管理するモデルだけで、MLX形式へ変換したモデルは表示されない。
- Ollamaはモデルの取得、管理、対話、API公開までを手軽に扱うツールで、MLXはApple Silicon向けの推論や学習処理を行う基盤である。
- `mlx-lm`では、モデルパスを変更するだけで複数のMLXモデルを呼び分けられる。
- OllamaモデルとMLXモデルも比較できるが、OllamaのHTTP APIとMLXのPython APIという呼び出し方の違いを比較プログラム側で扱う必要がある。
- 量子化では重みの表現精度を下げることで、モデル容量と実行時メモリを削減できる。
- 7Bモデルの元データは約15GBだが、4bit変換後は約4GBになった。
- M2 Pro・32GBでは、今回の7B 4bitモデルを約39 tokens/sec、最大メモリ約4.3〜4.5GBで動かせた。
- モデルが大きくなっても回答が必ず正しくなるわけではない。EvoLLM-JPにも条件不足や不正確な説明があった。
- RLT-7Bは日本語専用モデルではないが、今回の質問ではEvoLLM-JPより自然で具体的な日本語回答だった。
- 1問の結果だけでモデルの総合的な優劣は決められない。同じ評価質問を複数使う必要がある。
- 生成上限を300トークンにすると、両モデルとも回答途中で止まった。出力量も実験条件の一部になる。
- MLXでは推論だけでなく、Apple Silicon上でLoRAファインチューニングも行える。
- LoRAは元モデルの全パラメータではなく、小さな追加パラメータを学習するため、個人のMacでも比較的試しやすい。
- 今回の環境では、ゼロからの事前学習や7Bモデルのフルファインチューニングより、LoRAが現実的である。
- 最小RAGは「文書の分割 → Embedding → 類似チャンクの検索 → プロンプトへの根拠注入 → 回答生成」という流れで実装できる。
- 検索部分を共通にすれば、同じ根拠と質問を複数モデルへ渡して回答だけを比較できる。
- 今回は500文字の6チャンクから、質問に近い上位3件をモデルへ渡した。
- 固定文字数分割によって`OpenAI`が`O`と`penAI`に分かれた問題が、RAGの根拠にもそのまま残った。
- 答えがある質問では、RLT-7Bが根拠の重要点を最も具体的に拾った。TinySwallowは一部を狭く定義し、EvoLLM-JPは短いが誤字と過度な具体化があった。
- 答えがない天気の質問では、TinySwallowとRLT-7Bは回答を拒否できたが、EvoLLM-JPは根拠なしに「晴れ」と断定した。
- RAGで根拠を与えても、すべてのモデルが制約を守るわけではない。検索品質と回答モデルの指示追従を分けて評価する必要がある。
- 類似度が約0.32と低い検索結果しかなくても、現在の実装は上位3件を必ず渡す。今後は最低スコアによる足切りも検討できる。

## 今日出てきた重要用語

- MLX: Apple Silicon向けに設計された機械学習フレームワーク
- `mlx-lm`: MLX上でLLMの変換、量子化、推論、学習などを行うためのツール
- LoRA: 元モデルを保ったまま、小さな追加パラメータだけを学習するファインチューニング手法
- フルファインチューニング: モデル本体の全パラメータを更新する学習方法
- Hugging Faceモデル: Hugging Face Hubで配布されるモデルと設定ファイルのまとまり
- 4bit量子化: モデルの重みを主に4bitで表現し、容量とメモリ使用量を抑える方法
- tokens/sec: 1秒間に生成または処理できるトークン数
- Peak memory: 推論中に使用したメモリの最大値
- `IncompleteSnapshotError`: Hugging Faceのキャッシュに、リポジトリの一部ファイルが不足していることを示すエラー
- RAG: 外部文書から関連情報を検索し、その根拠をLLMへ渡して回答させる構成
- コンテキスト注入: 検索した文章を回答生成用のプロンプトへ組み込むこと
- 指示追従: モデルが「根拠だけで答える」などの指示を守れる性質

## 実行したコマンドと、その意味

```bash
uv venv .venv-mlx --python 3.12
```

Python 3.12を使うMLX専用仮想環境を作成した。既存のPython 3.14環境は変更していない。

```bash
source .venv-mlx/bin/activate
uv pip install mlx-lm
```

専用環境を有効にし、MLXでLLMを扱うための`mlx-lm`をインストールした。

```bash
mlx_lm.convert --hf-path MODEL_ID --mlx-path OUTPUT_PATH --quantize --q-bits 4
```

Hugging Faceのモデルを取得し、MLX形式へ変換して4bit量子化した。

```bash
hf download MODEL_ID FILES...
```

変換時のキャッシュに不足していた説明・ライセンス関連ファイルだけを追加取得した。

```bash
mlx_lm.generate --model MODEL_PATH --prompt "質問" --max-tokens 300
```

変換後のローカルモデルを読み込み、指定した質問への回答を最大300トークン生成した。

```bash
mlx_lm.chat --model models/RLT-7B-4bit
```

MLXモデルと会話形式でやり取りする。別モデルを使う場合は`--model`のパスを差し替える。

```bash
ollama list
```

Ollamaが管理しているモデルを一覧表示する。MLX形式のモデルは別環境にあるため、この一覧には表示されない。

```bash
du -sh models/EvoLLM-JP-v1-7B-4bit models/RLT-7B-4bit
```

変換後の各モデルがディスク上で使う容量を確認した。

```bash
python -m py_compile rag/rag_qa.py
```

モデルを実行する前に、Pythonコードの構文エラーがないことを確認した。

```bash
python rag/rag_qa.py
```

質問に近いチャンクを`bge-m3`で検索し、同じ上位3件をOllama上のTinySwallowとMLX上の2モデルへ渡して回答を比較した。

## まだ曖昧なこと

- MLXとOllamaで同じモデルを動かした場合の速度・メモリ・回答の差
- 4bit量子化によって回答品質がどの程度変化するか
- EvoLLM-JPとRLT-7Bを複数の日本語質問で評価した場合の得意・不得意
- RLT-7Bの推論能力が現れやすい数学・科学・コード問題での性能
- `mlx-lm`を使ったLoRA学習の具体的なデータ形式と設定
- MLXで学習したLoRAアダプターを統合し、必要に応じてOllamaで使うまでの変換手順
- チャンクの境界で単語を分断しない、Markdown構造を考慮した分割方法
- 類似度が低い場合に検索結果を採用しない最低スコアの決め方
- OllamaとMLXで生成時間をより公平に測る条件の揃え方

## 自分の言葉でのまとめ

OllamaとMLXは、どちらもローカルでLLMを動かせるが、同じ環境ではない。検索部分を共通化すれば、両環境のモデルへ同じ根拠を渡して比較できる。今回のRAGでは、答えがある質問はRLT-7Bが最も根拠に忠実だった一方、答えがない質問ではEvoLLM-JPが根拠なしに回答した。RAGは根拠を渡せば完成ではなく、検索の適切さとモデルが根拠を守るかの両方を確認する必要がある。
