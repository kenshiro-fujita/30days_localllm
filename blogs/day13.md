# ローカルLLM作成30日チャレンジ Day13(8月2日) TinySwallowで文章ツールを作ってみる

ローカルLLM作成30日チャレンジのDay13です。

前回までは、ストリーミングやJSON形式の出力など、PythonからTinySwallowを扱う部品を一つずつ試してきました。今回はそれらをアプリらしい形にまとめ、要約・文章改善・分類ができるCLIを作りました。

3つの機能が動けば気持ちよく終われると思っていましたが、文章改善の結果はなかなか微妙でした。

## 今日やったこと

### 3つのモードを持つCLIを作る

Day13の成果物として、`src/text_tool.py` を作りました。コードはCodexに一部分ずつ案内してもらい、自分で入力して動作を確認しています。

起動すると、最初に処理モードを選びます。

```text
モードを選んでください
1: 要約
2: 文章改善
3: 分類
```

選んだ番号に応じてsystem promptを切り替えます。TinySwallowのモデル名やAPI呼び出し部分は共通なので、機能ごとに同じコードを繰り返し書く必要はありません。

また、`1`〜`3`以外の番号や、空白だけの文章が入力された場合は、TinySwallowを呼ぶ前に終了するようにしました。CLIでも、受け取った値をそのまま次の処理へ渡さず、先に確認することが大切です。

### 要約モードを試す

最初に、ローカルLLMの特徴を説明した文章を要約させました。

```text
結果:
ローカルLLMは、自分のパソコン上で動作する大規模言語モデルです。

**特徴:**
- クラウドサービスへのデータ送信なしに利用可能。
- プライバシー保護の利点がある一方で、パソコン性能やモデルサイズにより回答速度や品質が変動します。
```

自分のパソコンで動くこと、プライバシー面の利点、PC性能によって速度や品質が変わることは残っています。元の文章より短くなっているので、要約としてはおおむね期待どおりでした。

一方で、依頼していないMarkdownの太字や箇条書きも付いています。前回のJSON出力と同じく、TinySwallowは形式について少し自由です。

### 文章改善は意味まで変えてしまう

次に、少し話し言葉に近い文章を改善させました。

```text
このアプリは文章を入れたら、要約とか改善とか分類ができて、ローカルで動くので便利だと思いました。
```

最初の結果では、次の説明が追加されました。

```text
また、ローカル環境で動作するため、インターネット接続がなくても利用できる点も魅力的です。
```

元の入力には、インターネット接続について書いていません。ローカルLLMでも、アプリの構成やモデルの取得状況によって通信が必要になる場合があります。

自分としては「自動的に」という言葉も余計だと感じました。今回のアプリは3つのモードから選ぶ仕様なので、入力すると全部の処理が自動的に行われるわけではありません。

そこで、「入力にない情報を追加しない」「情報を削除しない」とプロンプトへ追加しました。それでもTinySwallowは「自動的に」を追加し、元にあった「分類できる」という情報を削除しました。

さらに役割を「文章改善アシスタント」から「校正者」へ狭め、禁止する表現の例まで書きました。しかし、3回目も結果は次のようになりました。

```text
このアプリは、文章を入力すると自動的に要約や改善が行われ、さらにローカル環境でも動作するため非常に便利だと感じました
```

「自動的に」が残り、「分類」は消え、「便利」は「非常に便利」に強まりました。読みやすくはなっていますが、元の情報を保つという点では失敗です。

プロンプトを具体的にすれば必ず守られるわけではありません。文章の自然さと、意味や事実の保持は分けて評価する必要があると分かりました。

### Few-shotで精度を上げてみる

ここまで試したところで、正直なところ手応えがありませんでした。「LLMは間違える」という話はこれまでにも確認していますし、クラウドのLLMでも起こります。今回は失敗の再確認ではなく、どうすれば精度を高められるかまで試すことにしました。

最初に試したのはFew-shotです。指示だけを渡すZero-shotに対して、Few-shotでは望ましい入力と出力の例もプロンプトへ含めます。

文章改善のお手本を2組追加し、最初の文章をもう一度試したところ、結果はかなり良くなりました。

```text
このアプリは文章を入力すると、要約や改善、分類などの機能があり、ローカルで動作するため非常に便利だと思います。
```

「要約・改善・分類」と「ローカルで動く」は残り、「自動的に」「インターネット接続が不要」という追加も消えました。「非常に」と強めたり、「など」で別の機能もあるように見えたりする点は残りましたが、Zero-shotより明確に改善しています。

ただ、別の文章でも効くとは限りません。次は、ストリーミングの長所とコードが複雑になる短所を含む文章で試しました。

```text
このスクリプトは回答を少しずつ表示できて、待ってる間も動いてるのが分かるけど、コードが少し複雑になると思った。
```

TinySwallowは、「待ち時間を短縮する」という入力にない効果や、「コードを簡素化できる」という解決策を追加しました。良い点だけのお手本では、長所と短所が混ざる文章をうまく処理できなかったようです。

そこで、長所と短所の両方を残すお手本も追加しました。それでも結果は安定せず、校正ではなく相談への回答を始めることもありました。Few-shotは、例を増やせば単純に精度が上がるものではなさそうです。実際の入力パターンをカバーする例の選び方も重要だと分かりました。

### 生成した文章をもう一度検証する

次は、文章を1回生成して終わるのではなく、別のAPI呼び出しで結果を検証する処理を追加しました。

```text
文章を改善する
  ↓
情報の追加・削除・意味変更を検証する
  ↓
Pythonで合否を決める
  ↓
不合格なら原文を表示する
```

検証結果はJSON形式にし、追加・削除・意味変更を別々に出させました。しかしTinySwallowは、問題点を列挙しているのに `valid: true` と返しました。

```text
LLMの判定: True
Pythonの判定: False
追加: ['待ってる間も動いてるのが分かるけど', 'ユーザーの待ち時間を短縮し、進行状況を把握できる点が便利です']
削除: []
意味変更: []
```

そこで、最終判定はLLMへ任せず、追加・削除・意味変更のどれかが1件でもあればPython側で不合格にしました。不合格の場合は、問題のある改善文を採用せず、原文をそのまま表示します。

検証器も、原文にある「待ってる間も動いてるのが分かるけど」を追加情報と誤認しています。それでも「待ち時間を短縮」という本当に追加された情報も検出し、今回は安全側へ倒すことができました。

精度を上げるというと、モデルから常に正解を引き出すことだけを考えていました。しかし、怪しい出力を検出して採用しない仕組みも、アプリ全体の信頼性を上げる方法です。

### 分類モードとエラー処理を確認する

分類モードでは、次の文章を入力しました。

```text
明日の会議資料を確認してください。
```

結果は `依頼` でした。「確認してください」は相手に行動を求める文章なので、今回は妥当な分類です。

最後に、Ollamaとの接続などで問題が起きた場合に備え、API呼び出しを `try` で囲みました。`OpenAIError` が発生したときは、TinySwallowの呼び出しに失敗したことと、エラー内容を表示します。

READMEへの実行方法と注意点の追記は、長い定型文をnanoで編集する負担が大きかったため、Codexに代行してもらいました。自分では3モードを実際に操作し、それぞれの出力を確認しています。

## 今日のハマりポイント

### 最初の入力でターミナルから抜けられなくなった

最初の実行では、モード番号の `1` と要約対象の文章を続けて入力してしまいました。

```text
> 1ローカルLLMは、自分のパソコン上で動かせる大規模言語モデルです。……
```

プログラムはまだモード入力の完了を待っている状態でしたが、制御キーも文字として表示され、`Ctrl+C` や `Ctrl+D` でも抜けられませんでした。最終的には元のターミナルを閉じ、新しいターミナルでやり直しました。

再実行時は、まず `1` だけを入力してEnterを押し、「処理する文章を入力してください」と表示されてから本文を入力すると正常に動きました。

CLIは、今どの入力を待っているかを見ながら一つずつ操作する必要があります。また、今回のアプリは結果を一括表示するため、本文入力後に何も表示されない時間があります。Day11で試したストリーミングのほうが、処理中だと分かりやすい理由も改めて実感しました。

### Codexの編集指示が曖昧だった

エラー処理を追加するとき、Codexから「末尾のAPI呼び出しから結果表示までを置き換える」と案内されました。しかし、どこからどこまでなのかが明確ではありませんでした。

指摘後は、置き換える前のコードと、置き換え後のコードを両方示してもらいました。コード編集の案内では、「この辺り」ではなく、検索する行と置換範囲を具体的に示す必要があります。これは自分の操作ミスではなく、Codex側の案内不足でした。

## 今日の感想

要約・改善・分類の3つを選べるようになり、これまで作ってきた部品がようやく小さなアプリになりました。同じAPI呼び出しでも、プロンプトを切り替えるだけで役割を変えられるのは分かりやすかったです。

最初は3モードを動かしただけで、正直なところ手応えがありませんでした。そこからFew-shot、検証、Python側の判定、原文へのフォールバックまで進めたことで、ようやく精度改善を実装として考えられた気がします。

Few-shotは効く場合もあれば、別の入力では崩れました。検証用のTinySwallowも自己矛盾や誤検出を起こします。それでも、モデルの1回の回答だけに頼らず、複数の段階とプログラムのルールを組み合わせる考え方は収穫でした。次は、誤検出を減らす方法や、不合格時に再生成する方法も試してみたいと思います。
