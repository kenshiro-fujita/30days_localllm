# ローカルLLM作成30日チャレンジ Day23(8月11日) FT用データセットの設計を固める

ローカルLLM作成30日チャレンジのDay23です。

前回は、SFT、LoRA、QLoRAなどの用語と、学習時に使う設定をクイズ形式で確認しました。今回は実際に学習へ使うデータについて、何を正解とし、どの形式で保存するかを決めました。

まだモデルを学習させる段階ではありません。先に「どんな振る舞いを学ばせるのか」と「良いデータとは何か」を決める回です。コードを書く日とは違う難しさがありました。

## 今日やったこと

### 学習させる振る舞いを1つに絞る

Day21では、RAGは知識を外から補い、FTは回答形式などの振る舞いを調整するものだと整理しました。

今回は、そのとき決めた次の振る舞いをデータセットの目的にしました。

```text
会議メモや業務メモを、要点・決定事項・次の行動の3項目で簡潔に整理する
```

最新の社内情報などを覚えさせるのではなく、渡された情報を一定の形式へ整理する練習をさせます。

### system・user・assistantの役割を決める

学習データは、計画どおりmessages形式に固定しました。

- system：モデルに共通して守らせる振る舞い
- user：整理対象となる会議メモや業務メモ
- assistant：その入力に対する理想の正解

最初はsystemを「要点・決定事項・次の行動でまとめられるようにする」と考えました。ここは、学習の目的を書く場所ではなく、モデルへ直接渡す共通指示に直しました。

```text
会議メモや業務メモを、要点・決定事項・次の行動の形式で簡潔に整理してください。メモにない情報は推測しないでください。
```

Day22で確認した`--mask-prompt`を使うと、systemとuserは回答を作るための文脈として使いながら、assistantの正解部分を中心にlossを計算します。前日に学んだ設定と、今回のデータ構造がここでつながりました。

### 書いていないことを推測させない

設計で特に意識したのは、元メモにない情報をもっともらしく補わせないことです。

家族旅行についての架空のメモを自分で作って試しました。父親はインド、母親と長女は韓国、長男はイギリスを希望し、予算だけが全員で60万円以内と決まっている内容です。

韓国を希望する人が最多でも、旅行先が韓国に決定したとは書かれていません。そのため、正解例では希望を要点として整理し、決定事項は予算だけにしました。次の行動も書かれていないため、次の固定表現を使います。

```text
次の行動：
- メモから確認できる次の行動はありません
```

同じように、決定事項がない場合、行動はあるが担当者が不明な場合の表現も決めました。情報不足を隠すのではなく、「確認できない」と明示することも学習させたい振る舞いの一部です。

### 変更と矛盾の扱いを考える

会議メモでは、前半と後半で予定が変わることがあります。

例えば、公開日が15日から20日へ変わり、その理由も話し合われているなら、変更前後と理由を要約へ残します。一方、15日と20日の両方が書かれているだけで、どちらが正しいか判断できない場合は、勝手に後半を正解にしません。

```text
前半では15日、後半では20日になっている。明確な変更理由は議事録からは判定できない
```

このように、最終決定を整理する例だけでなく、矛盾を矛盾のまま伝える例もデータへ含めることにしました。

### 話題とメモの書き方に幅を持たせる

同じような学習例だけにならないよう、扱う話題を5分野に分けました。

- 開発仕様の検討
- マーケティング施策
- マネージャー定例
- 評価制度の検討
- 競合他社の動向調査報告

さらに、話題だけでなくメモの書かれ方も変えます。箇条書き、話し言葉や脱線を含む短い文字起こし、一部の情報が欠けた議事録などです。

完成された議事録ばかりで学習すると、雑なメモを整理する今回の用途から離れてしまいます。情報が足りない例や矛盾する例も、推測しない振る舞いを学ばせるための大事なデータだと分かりました。

### 50件を10件ずつ生成するプロンプトを作る

Day24では、シンセティックデータの候補を50件作る予定です。最初は、5分野を各10件ずつにすればよいと考えました。

件数の配分はそのままですが、一度に50件は生成しません。長い出力が途中で切れたり、後半の品質が落ちたりした場合に直しにくいため、1分野10件を5回に分けます。

「ランダムにして」と指示するだけでは、固有名詞や数値を入れ替えた似た例が増える可能性があります。そこで、会議の目的、登場人物、決定事項、担当者、期限、数値、文章の長さなど、変える観点も具体的に指定しました。

また、「JSONで出して」だけでは、JSON配列、Markdownのコードブロック、説明文などが混ざる可能性があります。生成プロンプトには、JSONLだけを出すこと、1行に1件とすること、前置きや件数報告を付けないことまで書きました。

データセットの品質基準は`dataset/dataset_spec.md`、実際に商用LLMへ渡す文面は`dataset/generate_prompt.md`へ保存しました。設計上の判断は自分で行い、文書の構成と文案はCodexに用意してもらい、自分でファイルを作成しました。

## 今日のハマりポイント

JSONとJSONLの違いは、説明だけではまだすぐに言葉へできませんでした。

今日の時点では、JSONLは「1行に1件のJSONを並べる形式」と覚えておきます。今回の1行には、system、user、assistantの3つが入ります。Day24に実物を生成し、Day25にPythonで読み込んで検証すれば、もう少し具体的に理解できそうです。

もう1つ難しかったのは、「良い要約」を言葉で定義することでした。重要度や緊急度で絞るだけでは、モデルが勝手に重要性を想像する余地があります。期限、結論、数値など、元メモから確認できる基準まで決める必要がありました。

## 今日の感想

FT用データは、正解例をたくさん並べればよいくらいに考えていました。しかし、情報がない場合や矛盾している場合まで先に決めておかないと、望んでいない推測も正解として混ざる可能性があります。

今回はまだ1件も本番データを生成していませんが、何を正解とするかの基準はかなり具体的になりました。次回はこの設計を使って実際に50件の候補を作り、どの程度指示どおりのJSONLになるか確かめます。
