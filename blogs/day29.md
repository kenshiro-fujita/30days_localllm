# ローカルLLM作成30日チャレンジ Day29(8月14日) ファインチューニングの最終評価とOllama配備

ローカルLLM作成30日チャレンジのDay29です。

前回は、TinySwallow、ファインチューニング前のQwen、ファインチューニング後のQwenを汎用質問で比較しました。今回は保存していた出力を使って最終評価をまとめ、最後にファインチューニングしたQwenをOllamaから動かせるところまで配備しました。

せっかく学習させたので、素直に強いモデルができていてほしかったです。しかし、実際の出力を見ると、そう単純ではありませんでした。

## 今日やったこと

### バラバラだった評価出力を質問ごとにまとめる

これまでの評価結果は、TinySwallow、base Qwen、tuned Qwen（今回の学習を適用したモデル）ごとに別ファイルへ保存していました。記録としては残っているのですが、同じ質問の回答を比べるたびにファイルを行き来する必要があり、かなり読みづらい状態でした。

そこでCodexに、保存済みの出力を質問単位で並べ直してもらいました。汎用評価では、1つの質問の下にTinySwallow、base Qwen、tuned Qwenの回答を並べています。FT評価では、入力、正解例、base Qwen、tuned Qwenの順にまとめました。

モデルを再実行したわけではありません。保存済み出力を再利用できたので、生成条件の違いを持ち込まずに比較できました。評価結果を残しておく意味を、最後になって実感しました。

### 全部を読まず、代表ケースで最終評価する

汎用評価は3モデルに10問、FT評価は2モデルに10問あります。これを最初から全部読み直すのは現実的ではありません。

今回は、Day27とDay28ですでに確認した評価を再利用し、明確な誤答、指定形式の違反、入力にない情報、途中終了を優先して整理しました。そのうえで、結論に影響する代表6ケースだけを最終確認の対象にしました。

最終的には、モデルごとに次の特徴が残りました。

- TinySwallowは読みやすい一方、RAGをRLHFと取り違えるような重大な誤答がありました
- base Qwenは安定する場面がありましたが、冗長化、途中終了、中国語混入、矛盾の見落としがありました
- tuned Qwenは情報保持や回答の方向性が改善した場面がある一方、形式崩れや学習由来の癖がありました

### tuned Qwenはシンプルな上位互換ではなかった

今回のFTでは、入力にある情報を素直に保持し、base Qwenより大きな捏造が減ったケースがありました。RAGの説明や業務ヒアリングでも、tuned Qwenの方が簡潔で方向性の良い回答を出した場面があります。

その一方で、学習させたかった「要点・決定事項・次の行動」の3区分を守れないケースが増えました。入力に担当者が書かれているのに「担当者未定」としたり、決定事項があるのに「ありません」と判断したりもしました。

さらに、学習データで使った表現が、関係の薄い汎用質問にも出ました。特定のタスクへ学習させても、その影響がそのタスクだけに閉じるとは限らないようです。

せっかく学習させたのにという気持ちはありますが、tuned Qwenがbase Qwenのシンプルな上位互換ではないというのが、今回の実際の結果でした。

### MLXのadapterをbase modelへ統合する

最終評価の後、任意課題だったOllama配備にも進みました。

この時点のtuned Qwenは、元のQwenとLoRA adapterが別々に保存された状態です。まずMLX-LMの`fuse`を使い、base modelへadapterの差分を統合しました。

元のモデルは4bit量子化版だったため、`--dequantize`を付けて統合しました。出来上がったモデルは約14GBです。

```text
base Qwen + LoRA adapter
        ↓ merge
統合済みQwen 約14GB
```

### GGUFへ変換する

GGUFは一般にGGML Unified Fileの略で、モデルの重み、構造、トークナイザーなどを1つにまとめる形式です。今回は、MLXで学習したモデルをOllamaへ持っていくために使いました。

使用していたMLX-LMの直接GGUF出力は、Llama、Mixtral、Mistral系だけに対応しており、今回のQwen2には対応していませんでした。そこで、`llama.cpp`の変換スクリプトを使いました。

変換後のF16 GGUFは約15.2GBでした。そのままでは重いため、Ollamaへの登録時に`q4_K_M`へ量子化しました。

```text
統合済みQwen
    ↓ llama.cpp
F16 GGUF 約15.2GB
    ↓ Ollamaで4bit量子化
tuned-qwen-day29 約4.7GB
```

### Ollamaからtuned Qwenを動かす

作成したGGUFを、`tuned-qwen-day29`という名前でOllamaへ登録しました。

```text
ollama run tuned-qwen-day29
```

最後に、会議メモを「要点」「決定事項」「次の行動」の3区分へ整理させました。

```text
要点：
- アプリ通知仕様について打合せを行った
- 配信タイトルは全角20文字までとする

決定事項：
- 画像添付機能をiOSとAndroidに対応させる
- 送信失敗時の再試行回数を最大3回とする

次の行動：
- 佐藤：仕様書の初案を作成する（10月15日まで）
```

3区分、数値、担当者、期限を保って回答できました。これは1問だけの疎通確認なので、量子化後も品質が完全に同じだとは言えません。ただ、MLXで学習したモデルをOllamaから実際に呼び出すところまでは完了しました。

配備後は、約14GBの統合済みモデルと約15GBのF16 GGUFを中間生成物として削除しました。再生成元のbase modelとadapter、Ollamaへ登録した約4.7GBの実用版だけを残しています。

## 今日のハマりポイント

最初のハマりは、評価結果がモデル別のファイルに分かれていて、とにかく読み比べづらかったことです。評価基準を決める以前に、出力を読むだけで疲れる構成でした。質問単位へ並べ直し、既存評価と代表ケースを使う方法へ変えました。

配備では、最初に使っていたPython環境にMLX-LMがなく、学習時の`.venv-mlx`へ切り替える必要がありました。また、MLX-LMのGGUF変換がQwen2へ対応していなかったため、途中からllama.cppを使う経路へ変更しました。

ツール1つで最後まで変換できたわけではありません。MLX-LMで統合し、llama.cppでGGUF化し、Ollamaで量子化と登録をする形になりました。

## 今日の感想

FTすれば元のモデルより良くなると思いたくなりますが、今回のtuned Qwenはシンプルな上位互換ではありませんでした。指定形式を守れなかったり、学習した表現が他の質問にも波及したりしています。

一方で、入力情報を保持して捏造が減った部分もありました。良くなったか悪くなったかを一言で決めるのではなく、何が変わり、どんな副作用が出たかを固定問題で見る必要があるのだと思います。

最後に、base modelとadapterを統合し、GGUFへ変換し、Ollamaから動かすところまでできました。モデルの学習だけでなく、評価して実際に使える形へ持っていくところまで一周できたのは、かなり大きかったかなと思います。
