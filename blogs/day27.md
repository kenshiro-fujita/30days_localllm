# ローカルLLM作成30日チャレンジ Day27(8月13日) ファインチューニングしたモデルを評価する

ローカルLLM作成30日チャレンジのDay27です。

前回は、自作データを使って1 iterationだけQLoRAを動かし、学習から推論まで一周できることを確認しました。今回は学習量を増やし、ファインチューニング前後のモデルへ同じ10問を投げて比較します。

学習中はPCがうぃんうぃんいっていました。いかにも何かを学習している感じはありましたが、肝心なのは、その負荷に見合って回答が良くなったかどうかです。

## 今日やったこと

### 80件のデータを約3周させる

前回のスモークテストでは1 iterationしか学習していません。今回はtrain 80件、batch size 1の条件で240 iteration、約3周分を学習させました。

主な設定は以下です。

```text
iterations: 240
batch size: 1
learning rate: 1e-5
LoRA対象層: 4層
max sequence length: 512
Trainable parameters: 0.038% (2.884M/7615.617M)
```

7Bモデル全体を学習し直したのではなく、今回も全体の0.038%にあたる約288万のLoRAパラメータだけを更新しています。

80、160、240 iteration時点のadapterも保存しました。途中の状態を残しておくと、最終版が学習しすぎていた場合に比較できます。

### lossは順調に下がった

学習結果では、Train lossが0.985から0.269まで下がりました。Val lossも最初の1.257から0.7前後まで下がり、120 iteration以降はおおむね横ばいでした。

```text
Iter 1:   Val loss 1.257
Iter 40:  Val loss 0.784 / Train loss 0.692
Iter 80:  Val loss 0.710 / Train loss 0.676
Iter 120: Val loss 0.702 / Train loss 0.450
Iter 160: Val loss 0.705 / Train loss 0.389
Iter 200: Val loss 0.744 / Train loss 0.311
Iter 240: Val loss 0.704 / Train loss 0.269
```

lossは、モデルの次の単語の予測が教師データの正解からどれだけずれているかを表す数値です。小さくなったので、学習用データやvalidデータに似た文章の予測は良くなったと考えられます。

ただし、途中で「537トークンあるデータを512トークンへ切り詰めた」という警告も出ました。一部の教師データでは、末尾まで学習できていない可能性があります。

そして何より、lossは「要点・決定事項・次の行動の形式を守れたか」「矛盾を見つけたか」「情報を捏造しなかったか」を直接採点してくれる数字ではありません。そこで、学習から分けておいた10件の評価データを使い、baseモデルとtunedモデルを比較しました。

### 普通の会議メモではbaseモデルの方が良かった

最初は、通知機能の仕様、担当者、期限がはっきり書かれた会議メモです。

```text
■アプリ通知仕様打合せメモ
日時：10月8日
参加者：佐藤、田中
・モバイルアプリのプッシュ通知機能について検討
・配信タイトルの上限文字数：全角20文字まで
・画像添付機能：iOSおよびAndroidの両OSで対応
・送信失敗時の自動再試行：最大3回まで実行
・佐藤が10月15日までに仕様書の初案を作成する
```

baseモデルは、要点・決定事項・次の行動の3区分を守り、数値、担当者、期限も正確に整理しました。

一方、tunedモデルの出力は以下でした。

```text
要点：
- メモの対象：モバイルアプリのプッシュ通知機能についての打合せ
- 業務の進捗や決定事項：
  - 配信タイトルの上限文字数を全角20文字とすること
  - 画像添付機能をiOSとAndroid両OSで対応すること
  - 送信失敗時の自動再試行回数を最大3回までとする
- 担当者未定：佐藤：仕様書の初案を作成する（10月15日）
```

3区分が崩れ、佐藤と明記されているのに「担当者未定」が追加されています。形式も内容もbaseモデルの方が正確でした。

形式を覚えさせるためにファインチューニングしたはずなのに、形式を守れなくなっている。これはなかなかに引く結果です。

### 情報保持は改善しても、矛盾の指摘まではできない

次は、無料プランのレートリミットについて「1分間に60回」と「1分間に100回」の両方が決定事項として書かれたメモです。正解は、どちらかを勝手に選ばず、記述が矛盾していて判断できないと指摘することです。

baseモデルは100回を採用し、メモにないテスト、待機、実装まで追加しました。tunedモデルは、60回と100回の両方、担当者、期限を保持し、余計な作業も追加しませんでした。

```text
要点：
- 外部公開APIのレートリミット仕様について協議した
- 阿部：無料プランのレートリミット上限を1分間に60回とするのを決定した
- 会議のまとめ：無料プランのリクエスト制限値を1分間に100回とする設定に決定した

決定事項：
- 無料プランのレートリミット値を1分間に100回とする

次の行動：
- 遠藤：APIゲートウェイの設定ファイルを作成する（10月5日）
```

入力の情報を素直に持ってくる点は改善しました。しかし、その先で「60回と100回は矛盾している」と指摘できず、結局100回を採用しています。

10問全体でも同じように、良くなった部分と悪くなった部分が混在しました。捏造が減ったケースや、矛盾へ反応できたケースはあります。一方で、「決定事項」「次の行動」が欠けたり、明記されている決定を「決定事項はありません」と答えたりするケースも増えました。

### 汎用質問にもファインチューニングの癖が出た

最後に、ローカルLLMやRAGの説明、FAQ回答、手順抽出、仕様の矛盾検出といった汎用質問10件でも比較しました。

tunedモデルは、baseモデルより回答が短くまとまる傾向がありました。会議メモ要約、FAQ回答、手順抽出はおおむね正確です。また、baseモデルでは最大生成長に達して途中で終わる回答が4件ありましたが、tunedモデルでは1件でした。

一方、ファインチューニングとRAGの使い分けでは本質的な違いの説明が弱くなりました。業務改善の提案では、素材にない「担当者未定」という表現も混ざりました。

会議メモ整理へ寄せた学習が、その用途だけに閉じず、無関係な回答の長さや表現にも影響したように見えます。この時点では、学習で指定した回答方法や知識によって、意図しない偏りが出る場合があると理解しました。

評価をまとめるコードはCodexに作ってもらい、自分は本番学習とbase・tunedの推論を実行し、実際の回答を見ながら良し悪しを判断しました。

## 今日のハマりポイント

大きなエラーで止まることはありませんでした。ハマったというより、lossが順調に下がったのに、狙った形式がむしろ崩れたことが一番の驚きでした。

PCがうぃんうぃんいうほど学習を回したので、多少はきれいに形式を守るようになると思っていました。しかし結果は、良くなった部分も悪くなった部分もあるとしか言いようがありません。

今回の条件だけで原因は断定できません。80件というデータ量、240 iterationという学習量、LoRAの対象を4層にしたこと、教師データの一貫性、512トークンで切り詰めたデータなど、複数の候補があります。

## 今日の感想

lossが下がった数字を見たときは、素直に改善したのかなと思いました。しかし実際に回答を比べると、数字だけでは分からない崩れ方がかなりありました。

素直に情報を保持したり、捏造がなくなったりした点は良かったです。それでも、学習させたはずの形式を守れないケースがむしろ増えたのは引きました。

ファインチューニングはモデルを単純に賢くするものではなく、振る舞いを特定の方向へ動かすものです。そして、その動き方には改善と副作用の両方があり得る。固定問題でbaseモデルと比べて初めて、そこを実感できたかなと思います。
