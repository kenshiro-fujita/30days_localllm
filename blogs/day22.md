# ローカルLLM作成30日チャレンジ Day22(8月7日) QLoRAの設定を読み解く

ローカルLLM作成30日チャレンジのDay22です。

前回は、RAGとファインチューニングの役割を整理しました。今回は、SFT、LoRA、QLoRA、adapter、mergeといった用語を確認し、Day20にMacで動かしたQLoRAの設定を読み解きました。

ファインチューニングは横文字も設定値も多く、分かるようなわからないような感覚があります。そこで今回は細かな最適化まで手を広げず、Day26で自作データへ差し替えるために必要な範囲へ絞りました。

## 今日やったこと

### SFTは正解例から振る舞いを学ぶ

SFTはSupervised Fine-Tuningの略で、日本語では教師ありファインチューニングと呼ばれます。

「教師あり」という名前のとおり、入力と理想の回答をセットで渡し、「この入力には、このように答えてほしい」という振る舞いを学ばせます。

例えば、会議メモを「要点・決定事項・次の行動」という形式へ整える入力と正解例を多数用意すれば、その回答形式へモデルを寄せることが期待できます。

RAGが必要な知識を回答時に外から渡す方法なのに対し、SFTはお手本を使って回答の形式や傾向を学ばせる方法です。

### LoRAとQLoRAで学習を軽くする

LoRAでは、モデル全体を書き換えず、元のモデルへ追加した少数のパラメータを学習します。巨大な教科書を丸ごと書き直すのではなく、用途別の薄い補足冊子を加えるようなイメージです。

Day20のスモークテストでは、RLT-7B全体の約76億パラメータに対して、学習対象は約288万パラメータ、全体の`0.038%`でした。保存されたadapterも約11MBです。

QLoRAでは、さらにベースモデルを4bitなどへ量子化し、メモリ使用量を抑えた状態でLoRAを行います。

当初は、軽量化したモデルを使うと学習の影響が相対的に大きくなるのではと考えました。しかし、量子化の主な狙いは学習効果を強くすることではなく、ベースモデルを少ないメモリで扱うことでした。Day20では、7B規模のモデルをピークメモリ約4.5GBで動かせています。

### adapterは何にでも付く部品ではない

LoRAで学習した差分は、adapterとしてベースモデルとは別に保存できます。同じベースモデルに対して、要約用や文章改善用など、用途別のadapterを付け替えられるのが利点です。

最初は、学習したadapterをほかのモデルにも付けられるのではと予想しました。ただし、adapterは学習時のベースモデルの構造や対象レイヤーに合わせて作られます。RLT-7B用のadapterを、構造の異なるTinySwallowへ自由に取り付けられるものではありません。

adapterの差分をベースモデルへ統合し、一つのモデルにする処理がmergeです。推論時にadapterを別途指定しなくてよくなる一方、用途別に付け替える手軽さは薄れます。今回の計画では、Day26はadapterの生成と推論確認までとし、mergeは行いません。

### Day20の設定を読み解く

Day20では、Mac上のMLX-LMで次の流れが最後まで動くことを確認しました。

```text
モデル読み込み
→ データ読み込み
→ 1回だけ学習
→ adapter保存
→ adapter付き推論
```

今回はCodexに保存済みの設定を確認してもらい、自分は各項目の意味と、Day26での扱いを整理しました。

主な設定は次のとおりです。

- learning rateは`1e-5`：1回の更新でパラメータをどれくらい動かすか
- iterationは`1`：パラメータを更新する回数
- batch sizeは`1`：1回の更新でまとめて処理するデータ数
- LoRA rankは`8`：adapterが表現できる変化の幅に関わる値
- 学習レイヤー数は`4`
- 最大シーケンス長は`128`トークン
- target modulesは明示せず、MLX-LMの標準設定を利用

Day20でiterationを1回だけにしたのは、品質を上げるためではありません。データを読み込み、学習してadapterを保存できることを確認するスモークテストだったためです。

### lossは正解例とのズレ

設定を読み解く途中で、Codexが説明なしにlossという言葉を使っていました。質問してみると、lossはモデルの予測と正解例のズレを数値化したものだと分かりました。ここは最初に説明が欲しかったところです。

- Train lossは、学習に使っているデータに対するズレ
- Val lossは、学習には使わない検証データに対するズレ

Train lossだけが下がり、Val lossが悪化する場合は、学習データへ寄りすぎる過学習が疑われます。

ただし、Day20は1 iterationだけです。lossが一度表示されても、改善傾向や回答品質までは評価できません。この段階では、lossを計算できるところまで学習処理が動いたという確認材料です。

また、`--mask-prompt`を使うと、systemとuserの文章は回答を考えるための文脈として渡しつつ、主にassistantの正解回答からlossを計算できます。

最大シーケンス長にも注意が必要です。上限が短すぎて正解回答の後半が切れると、途中で終わる回答を正解例として学ぶ可能性があります。Day20のサンプルは短いため`128`で収まりましたが、自作データでは実際の長さを確認する必要があります。

### Day26で変えるものを絞る

Day26で必ず変えるのは、Day25に作る自作データの場所と、adapterの保存先です。保存先を変えないと、Day20のスモークテスト結果と混同したり、上書きしたりする可能性があります。

iterationと最大シーケンス長は、自作データの件数や長さを見て変更を検討します。

一方、初回は次の条件を維持します。

- ベースモデルはRLT-7B 4bit
- batch sizeは`1`
- learning rateは`1e-5`
- LoRA rankは`8`
- 学習レイヤー数は`4`
- `--mask-prompt`は有効
- target modulesはMLX-LMの標準設定に任せる

一度に多くの条件を変えると、問題が起きた際に原因を切り分けにくくなります。まずは動作確認済みの条件をなるべく残し、自作データを読み込んで少ないiterationで学習できるかを確かめます。

## 今日のハマりポイント

今回は実行上のエラーはありませんでしたが、用語の似た印象に少し引っ張られました。

QLoRAの量子化は学習効果を強めるものではなく、主にメモリを節約するためのものです。また、adapterも任意のモデルへ付けられる共通部品ではありません。ざっくりした比喩は理解の入口になりますが、どこまで比喩どおりなのかを確認する必要がありそうです。

もう一つ、Codexがlossを未説明のまま使ったため、途中で意味を確認しました。知らない用語を雰囲気で流さず、その場で止めたことで、Train lossとVal loss、過学習の関係まで整理できました。

## 今日の感想

Day20ではQLoRAが動いたことだけを確認しましたが、今回は同じ結果を設定の意味から読み直せました。

特に、Day26で何を変え、何を変えないかが見えたのは大きな収穫です。いきなり良いモデルを作ろうとせず、まず変更点を絞って動作を確かめる。この進め方なら、ファインチューニングも少しずつ理解できそうかなと思います。
