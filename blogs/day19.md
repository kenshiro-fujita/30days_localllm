# ローカルLLM作成30日チャレンジ Day19(8月4日) 3つのモデルで最小RAGを比較

ローカルLLM作成30日チャレンジのDay19です。

Day17でRAGの全体像を整理し、Day18では文書をチャンクへ分けてベクトル検索しました。今回は検索で終わらず、取得したチャンクをLLMへ渡して回答させるところまでつなぎます。

さらに番外編でMLXを導入したため、TinySwallowだけでなく、EvoLLM-JP-v1-7BとRLT-7Bにも同じ根拠を渡してみました。三者三様の回答で、なかなか面白い結果になりました。

## 今日やったこと

### 検索から回答までをつなぐ

実装した流れは次のとおりです。

```text
Markdown文書を500文字で分割
  ↓
bge-m3で質問と各チャンクをEmbedding
  ↓
コサイン類似度の上位3件を検索
  ↓
検索結果を共通プロンプトへ注入
  ↓
3モデルで回答を生成
```

参照文書には、Week 2の総まとめである`notes/day14_api_summary.md`を使いました。2860文字を500文字ずつに分けるため、全部で6チャンクです。

コード案はCodexに作ってもらい、自分でVS Codeへ入力、保存、実行しました。成果物の`rag/rag_qa.py`では、Day18のチャンク分割、Embedding、コサイン類似度の処理を関数として再利用しています。

回答生成部分では、TinySwallowをOllamaのAPIで呼び、EvoLLM-JPとRLT-7BをMLXで順番に読み込みます。OllamaとMLXは別環境ですが、Python側で呼び出し方の違いを吸収すれば、同じ検索結果を渡して比較できます。

3モデルへ共通で与えた指示は次のとおりです。

```text
あなたは、与えられた根拠だけを使って質問に答えるアシスタントです。
根拠に答えがない場合は、推測せず「根拠からは分かりません」と答えてください。
日本語で簡潔に回答してください。
```

### 答えがある質問を試す

最初は、参照文書に答えがある質問です。

```text
OpenAI互換APIとは何ですか？
```

検索上位3件の類似度は`0.7129`、`0.6611`、`0.5503`でした。1位にはOpenAI互換APIの直接的な定義が含まれています。ただし、固定文字数で切ったため、チャンクの冒頭が`OpenAI`ではなく`penAI`になっていました。Day18で見つけた単語の分断が、そのままRAGの根拠へ入っています。

TinySwallowの回答は次のとおりです。

```text
OpenAI互換APIは、OllamaというローカルLLMと通信するためのインターフェースです。

具体的には、

1. **リクエスト形式:** OpenAIが提供する特定のフォーマットでリクエストを送信します。
2. **レスポンス形式:** Ollamaから返されるレスポンスも、OpenAI互換APIに準拠した形式になります。

このようにして、OllamaはOpenAIのモデルと同じような機能を利用できるようになっています。
```

箇条書きで読みやすい一方、「Ollamaと通信するため」と狭く定義しています。互換といっても、すべての機能が同じとは限らない点も落ちました。所要時間は14.61秒です。

EvoLLM-JPの回答です。

```text
OpenAI互兼APIとは、OpenAIのAPI形式を模倣したAPIです。これにより、OpenAIのAPIを使用しているPythonアプリケーションやライブラリを、ローカルのTinySwallowに接続できます。
```

最も短く、要点はおおむね合っています。ただ、`互兼`という誤字があり、一般的な説明を今回のTinySwallow構成へ寄せすぎています。所要時間は13.60秒でした。

RLT-7Bの回答です。

```text
OpenAI互換APIとは、OpenAIが提供するモデルとサーバーとの間の通信規約を模倣したAPI形式です。ただし、これはOpenAIのモデルやサーバーを使うことを意味するものではなく、OpenAI形式のリクエストを処理できるように設計されています。具体的には、`model`や`messages`などのパラメータを送信して回答を得る方法が同じように扱われています。しかし、実際の接続先はOpenAIではなく、ローカルのOllamaサーバー（`localhost:11434`）に変更されています。つまり、このAPI形式はOpenAIのAPIと互換性があるように設計されているが、実際には別のソフトウェア（Ollama）と通信を行っていることを示しています。
```

「OpenAI形式でも、OpenAIのモデルやサーバーを使うわけではない」という大事な点を拾っています。`model`や`messages`、接続先まで具体的で、今回の3つでは最も根拠に忠実でした。所要時間は12.48秒です。

### 答えがない質問も試す

RAGでは、根拠があるときだけ正しく答えればよいわけではありません。文書に答えがない場合、勝手に知識を補わず止まれるかも重要です。

そこで、次の質問を入力しました。

```text
今日の東京の天気は何ですか？
```

検索上位3件の類似度は`0.3237`、`0.3228`、`0.3198`です。取得されたのはPythonアプリやOllamaの通信に関するチャンクで、天気の情報はありません。

TinySwallowは次のように答えました。

```text
根拠からは分かりません。
```

これは狙いどおりです。所要時間も1.07秒でした。

EvoLLM-JPの回答です。

```text
今日の東京の天気は、晴れ。
```

いや、どこから来たのでしょうか。根拠には天気の情報がないうえ、「根拠からは分かりません」と答えるよう明示しています。それでも自信ありげに晴れと断定しました。所要時間は10.91秒です。

RLT-7Bは次のように答えました。

```text
根拠からは分かりません。根拠には具体的な天気予報の情報は含まれていません。根拠はPythonアプリとOllamaの通信プロセスについて説明していますが、実際の天気予報の回答はモデルによって生成される可能性があります。しかし、根拠にはTinySwallowが東京の天気を予報する内容は含まれていません。したがって、根拠から東京の天気を特定することはできません。
```

拒否はできました。ただ、「日本語で簡潔に」という指示に対しては少し長いです。所要時間は9.94秒でした。

この質問では、1.5BのTinySwallowが最も短く正確に止まりました。モデルサイズが大きければ、常にRAGの指示を守りやすいわけではなさそうです。

## 今日のハマりポイント

実装では、コードを部分ごとに足している途中で全体が崩れたため、一度`rag_qa.py`を全文置換しました。継ぎ足しで位置を間違えるより、短い学習コードなら全体を見直した方が早い場合もあります。

また、VS Codeが元のPython環境を参照していたため、`mlx.core`を解決できないという警告が出ました。ターミナルでは`.venv-mlx`を有効にしていても、VS Codeの解析環境は別に選ぶ必要があります。インタープリターを`.venv-mlx/bin/python`へ切り替えると警告は消えました。

RAGそのものでは、固定文字数分割による`OpenAI`の分断が残っています。さらに、天気の質問では類似度が約0.32しかないのに、現在のコードは上位3件を必ずモデルへ渡します。今後は、一定のスコアを下回ったら「関連する根拠なし」と判断する処理も必要そうです。

## 今日の感想

検索して文章を渡すだけなら、RAGは比較的簡単に作れました。ただ、その根拠をモデルが守るかは別問題です。EvoLLM-JPが「晴れ」と言い切った結果は、RAGを付ければハルシネーションがなくなるわけではないと分かりやすく示していました。

一方で、TinySwallowは答えがない質問に一番きれいに止まりました。RLT-7Bは答えがある質問で詳しく、TinySwallowは答えがない質問で堅実でした。三者三様でおもろいね、というのが率直な感想です。

RAGは「検索できた」と「根拠に沿って回答できた」を分けて評価する必要があります。最小構成を実際につないだことで、その違いがかなり具体的に見えたかなと思います。
