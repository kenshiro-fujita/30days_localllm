# ローカルLLM作成30日チャレンジ Day10(7月31日) 会話履歴を渡しても会話できるとは限らない

ローカルLLM作成30日チャレンジのDay10です。

前回は、PythonからTinySwallowへ1回だけ質問を送るスクリプトを作りました。今回は `messages` に発言を残し、複数回の会話ができるCLIへ発展させます。

コード上はきれいに会話履歴を渡せました。しかし、実際に会話してみると、TinySwallowは「カレー」を「日本語の学習」や「ラーメン」に変えてしまいました。皆さんは、履歴さえ渡せばAIが覚えてくれると思っていないでしょうか。自分は今回、履歴を渡す処理と、モデルが履歴を正しく使うことは別だと分かりました。

## 今日やったこと

### 3種類のroleを整理

Chat APIの `messages` では、各メッセージに `role` と `content` を設定します。

- `system`: AIの振る舞いや回答方針
- `user`: ユーザーの発言
- `assistant`: AIの回答

最初は「`messages` がシステムメッセージになるのか」と混乱しました。実際には、`messages` はすべての発言を入れるリストです。その中にある1件が `role: "system"` と指定されることで、システムメッセージとして扱われます。

```python
messages = [
    {
        "role": "system",
        "content": "日本語で簡潔に回答してください。",
    }
]
```

この区別が分かると、会話履歴の構造も理解しやすくなりました。

### 会話を繰り返すCLIを作成

Day10の成果物として、自分で `src/chat_cli.py` を作成しました。Codexにコードを一部分ずつ提示してもらい、途中で貼る位置が分からなくなったところでは、現在のファイルを確認してもらったうえで全体の形を整理しました。

CLIでは、`while True` で入力を繰り返し受け取ります。`exit` が入力された場合は、`break` でループを終了します。

```python
while True:
    user_input = input("You: ")

    if user_input == "exit":
        break
```

ユーザーの入力は `messages.append()` で履歴の末尾へ追加します。

```python
messages.append(
    {
        "role": "user",
        "content": user_input,
    }
)
```

この `messages` 全体をTinySwallowへ送り、返ってきた回答も `assistant` のメッセージとして追加します。

```python
response = client.chat.completions.create(
    model="hf.co/SakanaAI/TinySwallow-1.5B-Instruct-GGUF:Q5_K_M",
    messages=messages,
)

assistant_reply = response.choices[0].message.content

messages.append(
    {
        "role": "assistant",
        "content": assistant_reply,
    }
)
```

モデルが会話を自動で記憶しているのではなく、Python側がユーザーとAIの発言を保存し、リクエストのたびに履歴全体を送り直しています。

### カレーを覚えているか試す

作成したCLIを実行しました。

```bash
python src/chat_cli.py
```

最初に「私の好きな食べ物はカレーです」と伝え、続けて「私の好きな食べ物は何でしたか？」と質問しました。

TinySwallowの最初の回答は、カレーという言葉には触れたものの、次のような内容でした。

> 私は個人的なデータを記憶したり保持しません。

履歴内の「カレー」には気づいているようでしたが、「カレーです」と直接答えることはできませんでした。

そこで、`system` メッセージを次のように具体化しました。

```python
"content": "日本語で簡潔に回答してください。過去の会話内容について質問された場合は、messagesの会話履歴を参照して直接回答してください。",
```

これで改善するかと思いましたが、結果はむしろ悪化しました。

> あなたの過去の会話から判断すると、あなたは日本語を学ぶことが好きということですね。

日本語の学習については話していません。さらに別の実行では、最後に「ラーメンだと答えました」と、履歴にない内容まで作りました。

### 送信する履歴を表示して原因を切り分ける

コードが履歴を正しく送れていない可能性もあるため、Codexの案内でAPIを呼び出す直前に `messages` を一時的に表示しました。

2回目の質問時には、次の4件が正しい順番で入っていました。

1. `system` の指示
2. 「私の好きな食べ物はカレーです」という発言
3. TinySwallowの最初の回答
4. 「私の好きな食べ物は何でしたか？」という質問

これで、Python側の履歴管理は正しく動いており、TinySwallowが履歴をうまく使えていないと切り分けられました。確認後、デバッグ用の表示は自分で削除しました。

### 会話を長くしてもう一度試す

学習を終えた後、もう一度CLIを起動し、今度はカレーについて会話を長く続けてみました。

最初に「カレーが好き」「ゴロゴロ野菜が入っているカレーが好き」と伝えました。しかし、「俺が好きな食べ物なにか分かる？」と聞くと、TinySwallowはカレーと答えず、味や食材について逆に質問してきました。

そこで「さっきカレーが好きって言ったじゃん」と指摘すると、ようやくカレーと野菜の話を拾いました。

> 私はそのメッセージからあなたがカレーライスの何でもない野菜が大好きだと理解しました！

表現はかなり不自然ですが、その後はジャガイモやニンジンなどの大きな野菜が残っているカレーが好き、という話題をある程度引き継げました。最初の短い実験ではほぼ会話になりませんでしたが、明示的に訂正した後は、履歴の一部を後の回答へ使える場合もあるようです。

一方で、おすすめのレシピを聞くと、最初は質問を返すばかりで具体的なレシピを出しませんでした。さらに回答を促すと、今度は次のような材料を挙げました。

> 必要なのは「モディケーション・イン・ガラス」という製品です。

ほかにも「レトルトのゴロールカレー」という見慣れない商品名を出しています。会話のテーマだった「ゴロゴロ野菜」は引き継いでいるものの、レシピとしては存在を確認できない材料をもっともらしく作っており、そのまま信用して使える回答ではありませんでした。

この追加実験では、TinySwallowが履歴をまったく見ていないわけではなく、一部の情報を拾えることも確認できました。ただし、必要な情報を取り出せなかったり、訂正後にやっと話がつながったり、最後には架空と思われる材料を作ったりと、回答の安定性にはかなり課題がありそうです。

## 今日のハマりポイント

今日のハマりポイントは、会話履歴を正しく送信できても、会話が正しく成立するとは限らなかったことです。

最初は実装ミスも疑いましたが、送信直前の `messages` を表示すると「カレー」という発言は確実に含まれていました。それでも、TinySwallowは「日本語を学ぶことが好き」「ラーメン」といった存在しない情報を生成しました。

`system` の指示を具体的にすれば必ず改善するわけでもなく、今回はこちらの意図からさらに離れました。小型モデルでは、短い履歴でも文脈理解や指示追従が崩れる場合があるようです。

短い履歴では情報を取り違え、長めに会話した追加実験では、訂正後に「カレー」と「ゴロゴロ野菜」を部分的に引き継げました。一方で、会話が長くなると安定したわけではなく、最後には存在を確認できない材料名を使ったレシピを生成しました。

コードの問題かモデルの問題かを、実際の送信内容を表示して切り分けられたのはよかったと思います。また、モデルが履歴を参照できるかどうかを一度の回答だけで判断せず、会話を続けて観察する必要があると分かりました。

## 今日の感想

今日は、`messages` が会話全体を入れる箱で、その中の各メッセージが `role` によって分けられることを理解できました。

会話履歴を持つCLI自体は作れましたが、肝心の会話結果はかなり厳しいものでした。履歴を渡す仕組みが正しくても、モデルがその情報を正確に使えるとは限りません。

追加実験では、訂正すると「ゴロゴロ野菜」という話題を拾い直す場面もありました。完全に履歴を無視しているわけではないところが、逆に面白くも難しいところです。

「履歴がある」と「覚えて正確に答えられる」は同じではありません。部分的に会話がつながっても、最後に架空と思われる材料を出すことがあるため、もっともらしい回答ほど確認が必要だと感じた日でした。
