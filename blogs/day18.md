# ローカルLLM作成30日チャレンジ Day18(8月3日) 3種類のチャンクサイズでベクトル検索を比べた

ローカルLLM作成30日チャレンジのDay18です。

Day17では、RAGを「検索→文脈注入→回答生成」に分けて整理しました。今回は検索の前準備として、長いMarkdown文書を検索単位へ分ける「チャンク分割」を試しました。

チャンクという概念は知っていましたが、実際に文書を固定文字数で切ってみると、小さいチャンクと大きいチャンクのトレードオフが目に見えました。

## 今日やったこと

### 2860文字のMarkdownを読み込む

分割対象には、Day14で作った`notes/day14_api_summary.md`を使いました。Pythonの`Path.read_text()`で読み込み、文字数を確認します。

```python
from pathlib import Path


SOURCE_PATH = Path("notes/day14_api_summary.md")
CHUNK_SIZES = [300, 500, 1000]

text = SOURCE_PATH.read_text(encoding="utf-8")

print(f"ファイル: {SOURCE_PATH}")
print(f"文字数: {len(text)}")
```

実行コマンドは次の通りです。

```bash
python src/chunk_text.py
```

最初はファイル名を`chunk_test.py`と作っていたため、計画上の`chunk_text.py`を実行しようとすると「ファイルがない」と表示されました。ファイル名を修正して再実行すると、正しく読み込めました。

```text
ファイル: notes/day14_api_summary.md
文字数: 2860
```

### 300文字、500文字、1000文字で分割する

今回はまず、文章の意味やMarkdownの構造を考慮せず、先頭から固定文字数ごとに切る最小の方法を実装しました。

```python
def split_by_size(text, chunk_size):
    """文章を指定した文字数ごとに分割する。"""

    return [
        text[start:start + chunk_size]
        for start in range(0, len(text), chunk_size)
    ]
```

同じ2860文字の文書でも、指定する文字数によって分割数が変わりました。

```text
チャンクサイズ: 300文字
分割数: 10

チャンクサイズ: 500文字
分割数: 6

チャンクサイズ: 1000文字
分割数: 3
```

2860文字を300文字ごとに切ると10個、500文字で6個、1000文字で3個です。最後の余りも1チャンクとして数えられます。

### 先頭と末尾を表示すると、切れ方が見えた

分割数だけでは質の違いが分からないため、各チャンクの先頭と末尾も40文字ずつ表示しました。

300文字で分割した一部は、次のようになりました。

```text
2: 300文字 「表示 ... client = 」
3: 300文字 「OpenAI( ... 返ってくるデータの形などの」
4: 300文字 「決まりがある。 ... すべての機能が完全に」
```

1000文字で分割した境界では、次のチャンクが単語の途中から始まる例もありました。

```text
1: 1000文字 「# Day14 PythonからローカルLLMを使う流れ ... このように、O」
2: 1000文字 「penAIのAPIと似た決まりで呼び出せる ... モデル自身が会話を記」
3: 860文字 「憶するのではなく ... 不合格になった回答を再生成する方法」
```

`OpenAI`が`O`と`penAI`に分かれたり、「記憶」が別チャンクに分かれたりしています。固定文字数の分割は実装しやすい反面、文章や単語の区切りを保証してくれません。

小さいチャンクは話題を絞って検索しやすい一方、回答に必要な文脈が前後に分かれる可能性があります。大きいチャンクは文脈を残しやすい反面、関係のない話題も同じベクトルに混ざりやすくなります。

### 同じ質問でベクトル検索して比べる

分割して終わりでは、チャンクサイズによる検索の違いは分かりません。そこでDay16と同じ`bge-m3`とコサイン類似度を使い、同じ質問を300文字、500文字、1000文字のチャンクへ検索しました。

検索結果が長く、最初の表示はとても比べにくい状態でした。そこでCodexに表示処理を修正してもらい、サイズごとに上位3件と、各サイズの1位を並べた比較を表示するようにしました。

最初の質問では、OpenAI互換APIの定義が1つのチャンクに入るかを確認しました。

```text
OpenAI互換APIとは何ですか？
```

300文字では、検索1位は接続先の説明が中心で、直接的な定義は2位に入りました。上位1件だけをLLMへ渡す設定なら、必要な説明を外す可能性があります。

500文字では、直接的な定義が1位に入りました。

```text
penAIのAPIと似た決まりで呼び出せることを「OpenAI互換」と呼ぶ。
```

回答に必要な内容はありますが、`OpenAI`が前のチャンクの`O`と、このチャンクの`penAI`に分断されています。

1000文字でも1位に定義は入りましたが、Ollama、TinySwallow、各構成要素など、質問に直接必要ではない話題も多く含まれました。この質問では500文字が比較的使いやすそうでした。

### 質問を変えると、300文字が使いやすかった

1問だけで500文字が最適とは決められません。次は、会話履歴の管理に関する説明を検索しました。

```text
会話履歴はどこに保存されますか？
```

300文字の1位には、次の内容が入りました。

```text
過去の会話を毎回モデルへ渡す。モデル自身が会話を記憶するのではなく、Pythonアプリが履歴を管理する。
```

これなら1位のチャンクだけで質問に答えられます。一方、500文字と1000文字の1位は、どちらも「憶するのではなく」から始まっていました。「記憶」が境界で切れています。

1000文字の1位はスコア`0.5557`で、3種類の中で最高でした。しかし、文頭が切れ、質問とは関係のないストリーミングやJSON分類の説明も含まれています。類似度スコアが一番高いことと、回答材料として一番使いやすいことは別でした。

2つの質問を比較すると、1問目は500文字、2問目は300文字が比較的使いやすくなりました。どの質問にも共通する万能なチャンクサイズが、最初から決まっているわけではないと分かりました。

## 今日のハマりポイント

最初の実行で`src/chunk_text.py`が見つからず、Pythonから`No such file or directory`と表示されました。原因は、作成したファイル名が`chunk_test.py`になっており、実行コマンドの`chunk_text.py`と一致していなかったことでした。

エラーメッセージには、Pythonが探したファイルの絶対パスが表示されています。実際に作ったファイルのパスと比較することで、ファイル名の違いを切り分けられました。

もう一つは、固定文字数で切ると、単語や文の途中で分割されることです。これはプログラムのバグではなく、今回選んだ単純な分割方式の限界です。

また、Codexが最初に分割数と文章の切れ方を確認しただけでDay18を終えようとしました。学習計画にある「検索しやすさの違いを見る」には、実際のベクトル検索比較が必要でした。これはCodex側の進行確認不足で、その後に2つの質問を使った比較まで追加しました。

## 今日の感想

チャンクという言葉は知っていましたが、文字数を変えた実際の出力を並べると、なぜサイズが検索に影響するのかが分かりやすくなりました。

「小さいほど細かく検索できる」だけではなく、必要な文脈まで切り離す可能性があります。逆に大きすぎると、一つのベクトルへ複数の話題が混ざります。チャンクサイズに共通の正解があるわけではなく、文書と質問に合わせて実験するものなのだと理解しました。
