# ローカルLLM作成30日チャレンジ Day19番外編(8月4日) MLXで2つの7Bモデルを動かしてみる

ローカルLLM作成30日チャレンジのDay19番外編です。

ここまでは、Sakana AIのTinySwallowを中心に学習してきました。ただ、TinySwallowは1.5Bという小さなモデルです。軽さを優先して回答の悪さにイライラし続けるのも違うかなと思い、今回はApple Silicon向けのMLXを使い、少し大きな7Bモデルを試しました。

選んだのは、Sakana AIの日本語向けモデル`EvoLLM-JP-v1-7B`と、推論に特徴がある`RLT-7B`です。

## 今日やったこと

### MLX専用の環境を作る

使ったMacはM2 Pro、メモリ32GBです。7Bモデルを4bit量子化して動かすには十分そうでした。空き容量も149GiBあったため、元モデルと変換後モデルを置く余裕があります。

もともとのPython仮想環境は3.14.6でしたが、MLX関連パッケージとの互換性で詰まる可能性があります。既存環境は壊さず、`uv`でPython 3.12のMLX専用環境を作りました。

```bash
deactivate
uv venv .venv-mlx --python 3.12
source .venv-mlx/bin/activate
uv pip install mlx-lm
```

`mlx-lm`は、Hugging FaceのモデルをMLX形式へ変換し、量子化や推論を行うためのツールです。今回は`mlx-lm 0.31.3`と`MLX 0.32.0`が入りました。

この時点では、Ollamaの上にMLXを載せるというより、Ollamaとは別に、Apple Siliconへ最適化された実行ルートを用意したと理解していました。ただ、実際に2モデルを動かした後、まだ自分の中で両者の関係を正しく整理できていなかったことに気づきます。

### EvoLLM-JPを4bitへ変換する

最初に、日本語の汎用LLMとして公開されている`EvoLLM-JP-v1-7B`を変換しました。

```bash
mlx_lm.convert \
  --hf-path SakanaAI/EvoLLM-JP-v1-7B \
  --mlx-path models/EvoLLM-JP-v1-7B-4bit \
  --quantize \
  --q-bits 4
```

このコマンドで、Hugging Faceから元モデルを取得し、MLX形式への変換と4bit量子化をまとめて行います。

元モデルは約15GBですが、変換後は3.8GBになりました。4bit量子化によって、7Bモデルでもローカルで扱いやすい大きさに収まっています。

### RLT-7Bも同じ条件で変換する

次に`RLT-7B`も変換しました。RLT-7Bは日本語会話専用ではなく、数学や科学、コードなどの推論に特徴がある実験的なモデルです。

```bash
mlx_lm.convert \
  --hf-path SakanaAI/RLT-7B \
  --mlx-path models/RLT-7B-4bit \
  --quantize \
  --q-bits 4
```

こちらも元モデルは約15GBで、4bit変換後は4.0GBになりました。

### 同じ日本語の質問で比べる

変換が成功しても、実際に回答を生成できなければ意味がありません。両モデルへ次の質問を与えました。

```text
ローカルLLMを使う利点と注意点を、日本語で3つずつ簡潔に説明してください。
```

実行コマンドは次の形です。`--model`だけを変えて、質問と最大生成数は揃えました。

```bash
mlx_lm.generate \
  --model models/EvoLLM-JP-v1-7B-4bit \
  --prompt "ローカルLLMを使う利点と注意点を、日本語で3つずつ簡潔に説明してください。" \
  --max-tokens 300
```

EvoLLM-JPの生成速度は毎秒39.777トークン、最大メモリは4.256GBでした。日本語で箇条書きにし、3つずつ答えようとしていました。一方で、次のような説明もありました。

```text
速度: ローカルLLMは、クラウドLLMに比べて速度が速い。
```

ネットワーク遅延がないことは利点になり得ますが、クラウド側の計算資源やモデルサイズによっては、ローカルの方が遅い場合もあります。「常に速い」とは言い切れません。

プライバシーの説明でも、ローカルLLMが入力をローカルストレージへ保存すると書いていました。外部へ送らず処理できることと、自動的に保存することは別なので、ここも注意が必要です。

RLT-7Bは毎秒38.841トークン、最大メモリは4.476GBでした。冒頭は次のような回答です。

```text
1. データプライバシー保護：データがローカルで処理されるため、クラウドに送信する必要がない。これにより、機密情報の漏洩リスクが低減される。

2. 応答速度の向上：データがローカルに保存されているため、高速なアクセスが可能。遠隔地やネットワーク遅延の影響を受けることが少なく、リアルタイム応答が期待できる。

3. カスタマイズ性の向上：独自のデータセットや特定の用途向けにモデルを微調整できる。
```

今回の1問では、RLT-7Bの方が自然で具体的な日本語に感じました。ただし、応答速度の説明はEvoLLM-JPと同様に条件付きで読む必要があります。日本語が自然だから、内容まで正しいとは限りません。

どちらも最大300トークンに達し、注意点の3つ目の途中で終了しました。モデルだけでなく、生成上限も実験条件になると分かります。

### `ollama list`に2モデルがいない

動作確認後、いつものように`ollama list`を実行しました。ここで、EvoLLM-JPとRLT-7Bも一覧に追加されていると思っていました。

```text
NAME                                                    SIZE
bge-m3:latest                                           1.2 GB
qwen2.5:1.5b-instruct                                   986 MB
hf.co/SakanaAI/TinySwallow-1.5B-Instruct-GGUF:Q5_K_M    1.1 GB
```

しかし、表示されたのは以前からOllamaで使っていたモデルだけです。ここでようやく、OllamaとMLXは全然別の環境なのだと腑に落ちました。

```text
Ollama
├─ TinySwallow
├─ Qwen2.5
└─ bge-m3

MLX + mlx-lm
├─ EvoLLM-JP-v1-7B
└─ RLT-7B
```

Ollamaは、モデルの取得、一覧管理、対話、API公開まで揃ったローカルLLM実行ツールです。一方のMLXは、Apple Silicon向けの機械学習基盤です。今回使った`mlx-lm`が、その上でLLMを変換、量子化、実行しやすくしてくれます。

そのため、MLX形式で保存したモデルは`ollama run`ではなく、次のように呼び出します。

```bash
mlx_lm.chat --model models/RLT-7B-4bit
```

EvoLLM-JPを使う場合は、モデルパスを差し替えるだけです。

```bash
mlx_lm.chat --model models/EvoLLM-JP-v1-7B-4bit
```

同じMLX形式のモデルなら、`--model`の指定を変えるだけで簡単に呼び分けられます。比較用のPythonプログラムを作れば、同じ質問を複数モデルへ順番に送り、回答時間や内容を並べることもできます。

OllamaのTinySwallowまで含めて比較することも可能です。ただし、MLXモデルはMLXのPython API、OllamaモデルはOllamaのHTTP APIで呼び出すため、その違いを比較プログラム側で吸収する必要があります。

### MLXは学習にも使える

MLXがOllamaと別環境だと分かると、MLXを使う意味も見えやすくなりました。

Ollamaは主に完成済みのモデルを手軽に動かすための道具です。MLXでは推論や量子化に加えて、Apple Silicon上でLoRAファインチューニングもできます。

```text
Ollama
└─ 主に完成済みモデルを管理・実行する

MLX + mlx-lm
├─ モデルを実行する
├─ 量子化する
└─ LoRAで追加学習する
```

モデルの学習には、ほぼゼロから育てる事前学習、すべての重みを更新するフルファインチューニング、元モデルを残して小さな追加部分を学習するLoRAなどがあります。

今回のM2 Pro・32GBで現実的なのはLoRAです。7Bモデルをゼロから作ったり、全パラメータを更新したりするのではなく、比較的小さな追加パラメータだけを学習させます。

自分の中では、次のように整理できました。

> Ollamaは完成したLLMを手軽に使う環境で、MLXはApple Silicon上でLLMを動かすだけでなく、量子化やLoRA学習まで扱える基盤です。

## 今日のハマりポイント

### 量子化後の保存で止まった

2モデルとも、大きなモデルファイルのダウンロードと量子化が終わった後、保存直前に`IncompleteSnapshotError`が出ました。

EvoLLM-JPでは、次の3ファイルが不足していました。

```text
.gitattributes
LICENSE
README.md
```

RLT-7Bでは`.gitattributes`と`README.md`が不足していました。`mlx-lm`が最初にモデル変換用として取得したファイルと、保存時に完全なHugging Faceスナップショットとして確認するファイルが噛み合っていなかったようです。

不足分だけを`hf download`で取得しました。

```bash
hf download SakanaAI/EvoLLM-JP-v1-7B \
  .gitattributes LICENSE README.md

hf download SakanaAI/RLT-7B .gitattributes README.md
```

その後、同じ変換コマンドを再実行すると、モデル本体はキャッシュから読み込まれ、保存まで完了しました。約15GBを再ダウンロードせずに済みました。

これは自分のコマンドミスではなく、`mlx-lm`とHugging Faceのキャッシュ確認の噛み合わせで発生した問題でした。大きなダウンロードの後にエラーが出ると焦りますが、どこまで成功しているかを見るのは大事ですね。

## 今日の感想

1.5Bから7Bへモデルを大きくすると、動作がかなり重くなると予想していました。しかし、M2 ProとMLXの組み合わせでは、両方とも毎秒約39トークンで動きました。少なくとも短い文章を試す範囲では、待ち時間にイライラする感じではありません。

今回の質問だけなら、RLT-7Bの回答が一番読みやすく感じました。一方で、7Bへ大きくしても怪しい説明は残っています。「軽いモデルだから仕方ない」で終わらず、モデルを変えたときに何が改善し、何が残るのかを比べられそうです。

最初はMLX版のモデルも`ollama list`に出ると思っていましたが、別環境だと分かったことで、それぞれの役割がかなり整理されました。推論だけでなく、この先のLoRA学習にMLXを使えることも大きな収穫です。

まずは、TinySwallowだけにこだわらずに試せる土台ができました。次は同じ評価質問セットを使い、回答品質の差をもう少し公平に見たいと思います。
