## 今日やったこと

### 量子化とは何かを確認

最初に、量子化とは何かをCodexに説明してもらいました。

この時点での自分の理解は、次のとおりです。

```text
量子化とは、パラメータの個数を減らすのではなく、
各パラメータの数値を記録する細かさを下げて、
モデルを軽くする方法
```

LLMの中には、学習によって決まった大量の数値があります。

量子化では、その数値を細かく記録する代わりに、近い大まかな値で表現します。

```text
細かく記録するイメージ：0.123456
大まかに記録するイメージ：0.12
```

実際の量子化はもっと複雑ですが、今はこの感覚で捉えています。

TinySwallowは約15億個のパラメータを持っています。量子化しても、その約15億個という数自体を減らすわけではありません。各パラメータの値を記録する細かさを下げます。

その結果、ファイルサイズやメモリ使用量を減らせます。一方で、数値を大まかにするため、回答品質が低下する可能性があります。

また、モデルが軽くなると読み込みや推論が速くなる場合もありますが、必ず速くなるとは限りません。CPUやGPU、実行環境、量子化方式によっても変わるようです。

### TinySwallowの量子化方式を自分で確認

次に、自分でOllamaに保存されているモデルを確認しました。

```bash
ollama list
```

結果は次のとおりです。

```text
NAME                                                    ID              SIZE
hf.co/SakanaAI/TinySwallow-1.5B-Instruct-GGUF:Q5_K_M    54c14a1203d8    1.1 GB
```

現在使っているTinySwallowは `Q5_K_M` で、Ollama上では1.1GBと表示されました。

さらに、モデルの詳細情報も確認しました。

```bash
ollama show hf.co/SakanaAI/TinySwallow-1.5B-Instruct-GGUF:Q5_K_M
```

主な結果はこちらです。

```text
architecture        qwen2
parameters          1.54B
context length      32768
embedding length    1536
quantization        Q5_K_M
```

モデル名の `1.5B` は、約15億パラメータという意味でした。実際の表示では `1.54B` です。

そして、量子化方式が `Q5_K_M` であることも、ファイル名だけではなくOllamaの情報から確認できました。

`embedding length 1536` も表示されましたが、これはトークンをモデル内部で表す数字の並びの長さとのことです。EmbeddingはDay15で改めて学ぶ予定なので、今日は深追いしていません。

### GGUFとQ5_K_Mを分けて考える

途中で、`GGUF` と `Q5_K_M` は役割が違うことも整理しました。

```text
GGUF = モデルを保存・配布するためのファイル形式
Q5_K_M = モデル内部の数値を軽く表現する量子化方式
```

最初はモデル名の中に続けて書かれているため、ひとまとまりの言葉に見えていました。

しかし、GGUFはモデルを入れる箱のようなもので、Q5_K_Mは箱の中の数値をどう表現するかという違いです。

同じGGUF形式でも、F16、Q8、Q5、Q4など異なる精度のデータを保存できます。

一般的には、次の順で数値を細かく表現でき、ファイルサイズも大きくなりやすいと理解しました。

```text
大きくなりやすい・数値が細かい
F16 → Q8 → Q5 → Q4
小さくなりやすい・数値が粗い
```

ただし、実際の量子化方式では、すべてのデータを単純に同じビット数で保存するとは限りません。この並びは大まかな関係として捉えています。

### 公式ページでQ5とQ8を比較

次に、[TinySwallowの公式GGUF配布ページ](https://huggingface.co/SakanaAI/TinySwallow-1.5B-Instruct-GGUF/tree/main)を自分で開き、実際に配布されているファイルを確認しました。

確認できたのは次の2つです。

| 量子化方式 | ファイルサイズ |
|---|---:|
| Q5_K_M | 1.13 GB |
| Q8_0 | 1.65 GB |

現在使っている `Q5_K_M` は、`Q8_0` より約0.52GB小さくなっています。

Q5_K_Mは、Q8_0よりモデルを軽くしつつ、軽さと回答品質のバランスを取りやすい方式だと理解しました。

ただし、今回はQ5版とQ8版を実際に動かして回答を比べたわけではありません。回答品質や推論速度にどれくらい差が出るのかは、まだ分かっていません。

また、この公式GGUF配布ページではF16版を確認できませんでした。

## 今日のハマりポイント

今日のハマりポイントは、量子化そのものよりも、Codexの説明順でした。

最初にCodexが、F16の場合とQ5の場合の容量計算を出しました。しかし、その時点ではF16やQ5が何なのかをまだ説明していませんでした。

さらに、現在のモデル情報にはF16と表示されていないのに、F16の数字が出てきたため、「F16はどこで判定したのか」という疑問も出ました。

確認したところ、F16は実際のTinySwallowから判定したものではなく、量子化前とのサイズ差を説明するためにCodexが出した仮定でした。

```text
実際に確認したこと：
現在のモデルはQ5_K_M

説明のために出てきた仮定：
同じ数の値をF16で保存した場合
```

ここを最初に分けて説明していなかったため、話が分かりにくくなりました。

その後も `Embedding` など別の日に学ぶ言葉が入り、最終的には「全体的に分かるような分からないような内容」という感覚になりました。

そこで最後は、細かい方式の話を一度切り上げました。

```text
量子化とは、パラメータの個数は変えず、
各パラメータの数値を大まかに記録して、
モデルを軽くすること
```

今は、この一文が分かればDay4の最低限のゴールは達成としました。

## 今日の感想

Day4は、これまでの中でもかなり抽象的な日でした。

Day2のトークンは実際に分割結果を見られましたし、Day3の `temperature` は回答の変化を見られました。

一方、量子化はモデル内部の数値表現の話なので、目の前で何かが大きく変わるわけではありません。用語も多く、理解した感覚を持ちにくかったです。

それでも、モデル名に入っていた `Q5_K_M` が、ただの謎の文字列ではなくなりました。

今日の理解は次の4点です。

- 量子化では、パラメータの個数ではなく数値の細かさを変える
- 数値を粗くするとモデルを軽くできるが、回答品質が下がる可能性がある
- GGUFはファイル形式で、Q5_K_Mは量子化方式
- TinySwallowのQ5版は1.13GB、Q8版は1.65GBだった

`Q5_K_M` の内部で何がどう量子化されているのかまでは、まだ曖昧です。Q5版とQ8版で回答品質や速度がどれくらい変わるのかも試していません。

皆さんもローカルLLMのモデル名を見ると、英数字とアンダースコアだらけで面食らうことがあるのではないでしょうか。

今回は全部を理解しようとせず、まずは「軽くする代わりに、数値の細かさを少し失う」というところまでにしました。

次は、固定しておいた質問を使ってTinySwallowを評価し、モデルの得意・不得意を見ていく予定です。
