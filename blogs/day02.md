# ローカルLLM作成30日チャレンジ 第2日目(7月15日) トークンの仕組みを触って、日本語入力の重さを知った

ローカルLLM作成30日チャレンジの第2日目です。

今日はかなり軽めの日でした。

昨日はOllamaとTinySwallowを動かして、「ローカルLLMが自分のMac上で動く」というところまで確認しました。

今日はそこから少しだけ内部の仕組みに入って、LLMが文章をどういう単位で扱っているのかを見ていきました。

テーマは「トークン」です。

名前だけ聞くと少し専門用語っぽいですが、実際に日本語と英語の文章を分割して比べてみると、思ったより分かりやすかったです。

## 今日やったこと

### まずトークンとは何かを確認しました

最初に、Codexからトークンの説明を受けました。

トークンとは、LLMが文章を処理するための単位です。

人間は文章を文字や単語として読みますが、LLMは文章をそのまま読んでいるわけではありません。文章をいったん細かい部品に分けて、その部品を数値として扱っています。

この部品がトークンです。

今日の最初の理解は、こんな感じでした。

```text
トークンとは、LLMが文章を処理するための単位。
文字数とトークン数は、必ずしも一致せず、言語や状況で異なる。
```

また、文章をトークンに分ける仕組みをTokenizerと呼ぶことも確認しました。

Tokenizerは、LLM本体に文章を渡す前に、「この文章をどの部品に分けるか」を決める係のようなものです。

### 日本語と英語の短い質問を比べました

次に、自分でHugging FaceのTokenizer Playgroundを開いて、実際に文章を分割してみました。

今回は `Qwen/Qwen2.5-1.5B-Instruct` のTokenizerを使いました。

TinySwallowそのものではありませんが、TinySwallowはQwen系の流れに近いので、今日はQwenのTokenizerで観察しました。

まず入れたのは、この日本語です。

```text
ローカルLLMとは何ですか？
```

結果はこうでした。

```text
Characters: 14
Tokens: 12
分割: ロ / ー / カ / ル / LL / M / と / は / 何 / です / か / ？
```

人間には「ローカルLLMとは何ですか？」という短い質問に見えます。

でもTokenizer上では、`ローカル` が `ロ / ー / カ / ル` に分かれていました。

さらに `LLM` も1つのかたまりではなく、`LL / M` に分かれていました。

次に、同じ意味の英語を入れました。

```text
What is a local LLM?
```

結果はこうでした。

```text
Characters: 20
Tokens: 7
分割: What / is / a / local / L / LM / ?
```

ここが面白かったです。

英語の方が文字数は多いのに、トークン数は少なくなりました。

日本語は14文字で12トークン。英語は20文字で7トークンです。

皆さんは、文字数が多い方がLLMにとって重いと思うでしょうか。

自分も最初はなんとなくそう思っていました。

でも実際には、LLMにとっての重さは文字数ではなくトークン数で決まるようです。

### 日常文でも比べてみました

次に、もう少し普通の日常文でも試しました。

日本語はこちらです。

```text
今日は天気がいいですね。
```

結果はこうでした。

```text
Characters: 12
Tokens: 12
分割: 今 / 日 / は / 天 / 気 / が / い / い / です / � / � / 。
```

「今日は」「天気が」「いいですね」くらいに分かれるのかなと思っていましたが、実際にはかなり細かく分割されました。

しかも、「ね」の部分が `� / �` のように表示されていました。

これはTokenizer Playground上の表示の問題か、内部のバイト単位表現が見えている可能性がありそうです。

正確な理由はまだ分かっていませんが、少なくとも人間が自然に感じる分け方とは違うことは分かりました。

英語はこちらです。

```text
The weather is nice today.
```

結果はこうでした。

```text
Characters: 26
Tokens: 6
分割: The / weather / is / nice / today / .
```

英語の分割はかなりきれいでした。

文字数は26文字ありますが、トークン数は6です。

一方、日本語は12文字で12トークンでした。

このあたりで、日本語は人間にとって短く見えても、LLM内部では意外と重く扱われることがあるんだなと分かってきました。

### 業務文っぽい文章でも試しました

最後に、少し業務文っぽい文章でも試しました。

日本語はこちらです。

```text
会議では、来月のAI活用研修に向けて、参加者アンケートの設計と事前課題の内容を確認しました。
```

結果はこうでした。

```text
Characters: 46
Tokens: 49
```

表示上は、以下のように読めない断片がかなり出ていました。

```text
会��では、来月のAI活用���修に向けて、参加者アン��ートの��計と事前����の内容を����しました。
```

これはなかなかインパクトがありました。

人間には普通の業務文に見えますが、Tokenizer上ではかなり細かく分かれているようです。

特に、

- AI活用研修
- 参加者アンケート
- 事前課題

のような複合語は、人間には自然なまとまりに見えても、Tokenizerから見ると1つのかたまりとは限らないようです。

次に、同じ意味の英語を試しました。

```text
In the meeting, we reviewed the participant survey design and pre-work content for next month's AI training.
```

結果はこうでした。

```text
Characters: 108
Tokens: 21
```

英語は108文字、日本語は46文字です。

人間の目では英語の方がかなり長く見えます。

でもLLM内部では、日本語の方が49トークン、英語は21トークンでした。

これはかなり大きな差です。

今日いちばん分かりやすかったのはここでした。

```text
人間にとって短い文章が、LLMにとって軽い文章とは限らない。
```

### コンテキスト長についても確認しました

最後に、コンテキスト長についても確認しました。

コンテキスト長とは、LLMが一度に扱えるトークン数の上限です。

ここで大事なのは、コンテキスト長は文字数の上限ではなく、トークン数の上限だということです。

入力文、システム指示、会話履歴、資料、そして出力予定分を含めて、その範囲に収める必要があります。

つまり、日本語でトークン数が増えやすい場合、同じコンテキスト長でも入れられる文章量が減ります。

これはRAGにもつながります。

RAGでは、検索した資料をプロンプトに入れてLLMへ渡します。

日本語の資料が見た目以上にトークンを使う場合、LLMに渡せる資料量が減ります。

なので、業務文書を扱うAIを作るときに、

```text
資料を全部そのままLLMに投げればいい
```

とはなりにくいんだなと感じました。

## 今日のハマりポイント

今日は大きなハマりはありませんでした。

ただ、軽く驚いたポイントは2つあります。

1つ目は、日本語の表示がかなり崩れて見えたことです。

`今日は天気がいいですね。` の「ね」が `� / �` のように表示されたり、業務文の一部が読めない断片になったりしました。

これはエラーというより、Tokenizerが内部でどう分解しているかが人間に読みやすい形で見えていない、ということなのかなと思います。

ただ、正確な理由はまだ分かっていません。

ここは今後、TinySwallowそのもののTokenizerや、GGUF化されたモデルと元モデルのTokenizerの関係を見るときに、もう少し理解できそうです。

2つ目は、日本語と英語の差が想像以上に大きかったことです。

特に業務文では、日本語46文字が49トークン、英語108文字が21トークンでした。

人間の目では英語の方が長いのに、LLM内部では日本語の方が倍以上重い。

これはなかなか直感に反します。

でも、ローカルLLMやRAGを扱う上ではかなり大事な感覚だと思いました。

## 今日の感想

Day2は軽めでしたが、けっこう大事な回だったと思います。

昨日は「ローカルLLMが動いた」「でも回答は普通に間違える」という入口でした。

今日はそこから一歩だけ進んで、LLMが文章をどう受け取っているのかを見ました。

トークンという言葉だけ聞くと抽象的ですが、実際に日本語と英語を並べてみるとかなり分かりやすかったです。

特に、業務文っぽい日本語が思った以上にトークンを使うことは、今後かなり効いてきそうです。

社内の資料やFAQ、議事録をAIに読ませたいとなったとき、日本語の文章をどれだけ渡せるかは重要になります。

その意味で、今日の学びはRAGにもつながる前提知識になりそうです。

今日の結論はこれです。

```text
LLMは文字ではなくトークンで文章を扱う。
日本語は見た目よりトークンが重くなることがある。
だから、長文資料やRAGではトークン効率を意識する必要がある。
```

次はプロンプトと出力の変化を見ていく予定です。

同じローカルLLMでも、聞き方や条件の出し方でどれくらい回答が変わるのかを試す回になりそうです。
