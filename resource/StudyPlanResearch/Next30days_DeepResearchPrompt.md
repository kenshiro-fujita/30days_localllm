## プロンプト本文

あなたは、ローカルLLM、RAG、情報検索、VectorDB、Knowledge Graph、GraphDB、GraphRAG、LLM評価に詳しい技術リサーチャー兼学習設計者です。

以下の背景と制約をすべて踏まえ、120日チャレンジの第2フェーズに当たる「日本語ナレッジ検索基盤30日チャレンジ（Day 31〜60）」の、実行可能な学習計画を作成してください。

単なる技術一覧や一般論ではなく、最新の一次情報をDeep Researchで調査し、初心者寄りの学習者がMac上で毎日少しずつ手を動かして完走できる、日別の具体的な計画にしてください。

### 1. 120日チャレンジ全体における位置づけ

120日チャレンジ全体の最終目的は、次の状態になることです。

> ローカルLLM、VectorDB、GraphDB、承認制AIエージェントを小さく実装し、最後にAIX業務を模したPoCシナリオで、評価、安全性検証、導入提案まで行えるようになる。

全体は次の4フェーズです。

1. Day 1〜30：ローカルLLM入門（完了済み）
2. Day 31〜60：日本語ナレッジ検索基盤（今回作成する計画）
3. Day 61〜90：承認制ローカルAIエージェント
4. Day 91〜120：AIX PoCシミュレーション

今回のDay 31〜60は独立した作品作りではなく、Day 61以降のAIエージェントが利用する検索基盤を構築し、技術選定を説明できるようにする期間です。

### 2. 学習者の前提

- 現在は非エンジニア職だが、レガシー企業で約3年弱の業務システム開発経験がある
- 情報工学・機械学習の専門家ではない
- Python、CLI、API、Git、VS Codeの基礎的な操作経験はある
- 将来はAI研究者や本番AI基盤の専門エンジニアではなく、「AI機能のPoC設計者・実装理解者・業務接続役」として社内AIX(AIの社内推進)に関わりたい
- 学習では完成品をAIに丸投げせず、自分で実装し、処理の意味を説明できることを重視する
- 数式やアルゴリズムは、検索方式を選び、失敗原因を切り分けられる程度まで理解したい。証明や研究者レベルの深掘りは不要

- MacBook Pro

### 4. 完了済みの最初の30日で実際に学んだこと

Day 1〜30では、次を一通り体験済みです。

- OllamaによるローカルLLM実行
- トークン、Attention、次トークン予測、生成パラメータ、量子化、GGUFの基本
- Python仮想環境とPythonからのAPI呼び出し
- OllamaのOpenAI互換Chat API
- `bge-m3`によるEmbedding
- Markdown文書をチャンク分割し、NumPyのコサイン類似度で総当たり検索する最小RAG
- 同じ検索根拠をRLT-7B、TinySwallow、EvoLLM-JPへ渡した比較
- RAGなし／ありの固定質問による評価
- Qwen2.5-1.5B-InstructへのLoRAファインチューニング
- base modelとtuned modelの比較
- adapterの統合、GGUF変換、Ollamaへの登録
- Train lossだけでは実用品質を判断できず、未学習の固定問題による評価が必要だという理解
- RAGは外部知識を回答時に補い、FTは回答形式や振る舞いを調整する、という使い分け

最小RAGでは、検索したチャンクをLLMへ渡すところまでは実装しました。ただし、永続的なVectorDB、文書更新、メタデータ検索、複数の検索方式、GraphDB、GraphRAG、体系的なRAG評価は未経験です。

### 5. 現時点で残っている問い

- ファイル上の総当たり検索をVectorDBへ移すと、機能、速度、運用、更新方法は何が変わるのか
- 日本語文書に対して、チャンクサイズ、オーバーラップ、見出し構造、検索件数、類似度閾値、メタデータが検索と回答へどう影響するか
- dense retrievalだけでなく、BM25などのkeyword/sparse検索やhybrid searchをいつ使うべきか
- rerankerは今回の30日で扱う価値があるか。扱うなら、どの段階・どの軽量モデルが妥当か
- 回答に出典を表示するだけでなく、その根拠が回答を本当に支持しているかをどう評価するか
- 根拠がないときに無理に回答しない仕組みをどう設計・評価するか
- 人、組織、プロジェクト、文書、課題、OKRなどの関係を、GraphDBのノードとエッジへどう落とすか
- オントロジーやスキーマ設計を、初心者が業務ナレッジ検索へどう結び付けるか
- Vector検索とGraph検索は、どの質問で差が出るのか
- GraphRAGは何を指す言葉なのか。Microsoft GraphRAGのような方式、Knowledge Graphを併用するRAG、単純なVector＋Graph検索を区別して理解したい

### 6. 今回の30日の主目的と配分

主目的は、日本語文書を対象に、検索から回答、根拠表示、評価までをローカルで実装し、VectorDB、GraphDB、GraphRAGの使い分けを説明できる状態になることです。

時間配分の目安は次のとおりです。

- VectorDB / RAG：60%。自分でPythonコードを書く
- GraphDB / Knowledge Graph：25%。スキーマ設計と概念理解を重視する
- Hybrid / GraphRAG：15%。入口と最小デモまで。深追いしない

GraphDBではCypherなどのクエリ言語の暗記を目的にしません。学習者本人は、業務上の意味、Graphスキーマ、ノード、リレーション、検索経路を設計・説明します。定型的なCypherやPython接続コードはAIに生成させても構いません。

逆にVectorDB/RAGでは、取り込み、分割、Embedding、保存、検索、プロンプトへの根拠挿入、出典表示、評価の主要部分を本人がコードとして追える計画にしてください。最初からLangChainやLlamaIndexへ全面依存し、処理がブラックボックスになる計画は避けてください。必要性を理解した後に比較目的で触れるのは構いません。
